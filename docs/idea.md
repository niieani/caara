What we're after here is:

Codex today can spawn subagents. These subagents have to use be built-in Codex subagents, or use a OpenAI Responses SSE-compatible transport.
The aim of this project is to use the same external protocol (OpenAI Responses), but under the hood spawn actual, real external agents, such as Claude Code, Gemini/Antigravity, Cursor, and so on, and relay the messages from Codex to them, and from external agents back to Codex, while maintaining/resuming a session, and managing these state of these agents.

The only client/consumer of this API is and will be Codex (the managing agent session), and thus it must be /v1/responses-shaped. We will probably expose different clients at different base paths though, so base_url might be different for different agents, and maybe even for different configurations of these agents. We might make it configurable in caara e.g. to map /$name/v1 to a given agent, e.g. /claude-opus/v1 to be configured to use the claude code as the "backend" / "driver" with model opus and a specific reasoning effort, etc. Some clients might work via ACP, some might have to be spawned directly via CLI. For first version I'd like to start with just claude code support.

The external agents all support session durability, by providing a session ID of some sort. Since Codex can keep the agent running and ask follow-up questions (subagents aren't necessarily just 1 question + 1 answer), Caara needs to store that session id and be able to map the input somehow to that ID, and persist it, so when we resume work, we can resume the correct external agent. In some cases, these external agents might be initialized/started once when the agent is first called, and persist in memory until the subagent is closed by the managing Codex (better for performance), or by some timeout after idle. In some cases it might be easier to just spawn a fresh CLI agent for every turn - that might depend on the implementation of that external agent and what interfaces it exposes.
